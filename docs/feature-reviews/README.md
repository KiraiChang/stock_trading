# 專案功能檢討

每一期的紀錄回答三個問題：哪些功能已經能解決使用者的問題、下一版最值得交付什麼、上次的決定帶來了什麼結果。檢討時機與歸檔方式見 [開發工作流程](../development-workflow.md#定期功能檢討)。

| 檢討日期 | 主題 | 本期方向 |
|---|---|---|
| 2026-11-19 | [首次功能盤點與可用首版](./2026-11-19-first-usable-release.md) | 建議先交付台股盤後交易計畫，優先接通觀察清單與交易分析，補齊資料日期和失敗狀態。 |

## 每期怎麼記

以台北日期命名為 `YYYY-MM-DD-主題.md`。每期加一列到上方索引，最新一期放最上方。回看舊決定時，把驗證結果與改判原因寫進新一期，讓讀者能看出方向何時改變。

可從下面的骨架開始。每項功能有驗證就附上測試、試用或文件位置，證據不足時標明「待驗證」。

```markdown
# YYYY-MM-DD 功能檢討：主題

檢討期間、版本與範圍

## 對照前一期

上一期承諾、實際結果、延後或改判原因。

## 功能盤點

| 功能 | 解決的問題 | 可用程度與證據 | 本期取捨 |
|---|---|---|---|

## 下一版與驗收

目標使用者、要走完的流程、優先項目、可觀察的驗收條件。

## 下一期回看

要回看的假設、結果與相關 issue／todo。
```
